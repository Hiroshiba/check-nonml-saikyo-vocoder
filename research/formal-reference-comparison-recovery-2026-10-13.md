### 原因について確定していること・していないこと

- 確定しているのは、上記3プロセスのSIGKILL終了、成功済み件数、およびその時点の未完分である。
- 実行中のメモリ増加は観測した。ただし、OSがメモリ不足で終了させたことを示すOOM記録は得られていない。したがって「OOMが原因だった」「メモリリークを特定・修正した」とは結論しない。
- SIGKILLでは、その停止そのものに対するPython例外のスタックトレースが残らない場合がある。終了コード、直前までの標準出力・標準エラー、成功ファイル、起動時刻を併せて残す。後続評価の `FileNotFoundError` は未保存波形を読めない結果であり、初回停止原因の証拠とは区別する。
- 10件ごとの新プロセス化は、長く生きるプロセスに状態・使用メモリが蓄積する可能性に対処する運用変更である。最適な分割数、メモリ使用量の上限、原因の解消を証明するものではない。

## 2. 維持する条件と、変更する条件

維持するもの：

- 固定120録音、入力PCM、入力IDと元の順序、標本化周波数、事前固定の音声例
- 測定開始時の合成・評価ソース、公開実装・重み・依存環境、HNM v3
- 各録音の合成seed 0、合成1スレッド、CPU実行、各方式のネイティブ出力
- UTMOSv2の固定条件、抽出seed 20261012、反復1、CPU4スレッド
- 既に成功した744件のJSON/npy、および入力・出力の条件が一致する保存済み音響評価とMOS
- 全長・方式ごとの共通先頭区間・欠測を分離する集計方法

変更するのは、未完の録音を処理するワーカーの**プロセス寿命と分割境界**だけ。未完リストを元の入力順に抽出し、1回に最大10件、同時に1プロセスだけ実行する。最後のまとまりは10件未満になり得る。全120録音の正式測定の続きを分割しているのであり、少数推論のテストやスモークではない。

事前に予定したFACodec5回、HiFi-Glot11回、SiFi-GAN8回、計24回のワーカーを実行し、216件を回収した。成功済み5方式と、上記3方式の初回成功済み録音は再合成していない。再合成の品質を見て出力を選ぶ操作もしていない。

各録音の前にseedを再設定する実装と入力順序は維持する。ただし、プロセスを起動し直すとライブラリ内部の状態や初回処理が変わり得る。**同一の名目条件を維持することと、未実施の連続実行に対する波形のビット一致を証明することは別である。** 比較のための重複合成・自己一致測定は行わず、プロセス分割を実行条件の変更として公開記録に残す。

## 3. 初回と回収処理を重ねない

初回の音響段階・MOS段階が両方終了したことを示す `runs/formal-measurement-process.json` を待ってから回収を始める。初回MOSを中断して回収を割り込ませない。同じ評価途中JSONへ並行して書き込ませない。

初回の終了コードが非ゼロでも、保存済みの成功結果は有効な途中成果である。非ゼロを隠して「全件成功」とするのではなく、初回のコードを保存し、不足分を回収した後の完了状態を別に判断する。

測定開始情報は次のとおり。

- 初回開始：2026-10-13 04:37:48.919662 UTC
- ローカル実行commit：`c00edae9ed07a258d43c7c3e8bf8bb9d6ea7c595`
- リモート側の同一内容commit：`2308accfd3069e19fed852e1334b8269da761b5a`
- 両commitの同一Git tree：`53cb6143cf00340b8a5b1b328571aefd9aabbc07`

commit表記が異なる経緯と同一treeの確認は `execution.json` に残す。測定ソースの照合では、実行時の `contract.json.source_hashes` を使い、現在のブランチ名だけを根拠にしない。

## 4. 回収の手順

回収用の制御スクリプトはGit管理外の `runs/recover-formal-workers.py`。合成・評価の測定packageは編集しない。次の処理を行う。

1. 初回終了記録の存在を確認する。既存の `recovery/` があれば上書きせず停止する。
2. 契約に記録された全ソースSHA-256と、入力仕様のID・順序・標本化周波数を照合する。ワーカー自身も各入力npyのSHA-256と準備済み実装を照合する。
3. 初回の `processes.json`、終了記録、各方式の初回 `implementation.json` を保存する。既存の成功JSONとnpyのSHA-256を、後から変化を調べられる一覧にする。
4. `inputs.json` の元の順序を保ち、native JSONがないか `status != measured` の録音だけを方式ごとに抽出する。
5. 最大10件ずつの入力仕様JSONを保存し、凍結済み `vocoderbench.references.worker` を新しい直列プロセスで実行する。`--retry-failed` を付け、存在する失敗JSONはワーカーの失敗履歴へ残す。
6. 各起動について、入力IDと入力仕様、そのSHA-256、完全なコマンド、開始・終了時刻、ログ、終了コード、成功ID、初期化を含む実装情報を記録する。各まとまりの先頭録音も `cold_first_case` として残す。
7. 10件以下でも `-9` が出た場合は、その方式の残りのまとまりを続けて起動しない。他方式の独立した回収は進め、未完と非ゼロ終了を残して再判断する。10件なら必ず成功するとは扱わない。
8. 最後に既存成功JSON/npyのSHA-256を再照合する。変わっていれば回収成功とせず停止する。
9. 回収履歴・制御スクリプトの全文とSHA-256・成功ファイル保持の照合結果を `preparation.json` へまとめる。`processes.json` には初回の失敗と回収履歴を含めた最終状態を保存する。
10. `--stage mos --retry-failed` で、保存波形の不足している音響評価・MOSと最終HTML/JSONを作る。条件が一致する完了済み評価は再利用する。`--stage all` による全方式の再合成はしない。

### 実行コマンド

以下は今回使用した入口の記録。回収と後続評価は終了しており、同じ結果を作り直すために再起動しない。途中回収を再現する場合は、リポジトリのルートで初回処理が終了し、同じ実行に属する条件・成功波形・キャッシュが残っている状態を前提とする。

```sh
# 初回終了を待ち、回収、未完評価、各段階の終了記録までを直列に進める。
bash runs/continue-formal-measurement.sh
```

制御スクリプトが起動するワーカーの形式は次のとおり。`METHOD` と `BATCH_JSON` は、手順4で抽出した未完分と手順5で保存した入力仕様を指定する。全件の `inputs.json` を使って成功済み録音を測り直す目的には使わない。

```sh
.cache/references/env/bin/python -m vocoderbench.references.worker \
  --method "$METHOD" --runtime-cache "$PWD/.cache/references" \
  --inputs "$BATCH_JSON" \
  --output "$PWD/runs/formal-hnm-v3-reference-120/native/$METHOD" \
  --threads 1 --seed 0 --retry-failed
```

各起動の上限は10800秒で制御スクリプトが管理する。HNMを起動する必要がある場合のPythonは本体 `.venv/bin/python` だが、今回HNMは120件成功しているため再実行対象ではない。

回収後の評価コマンド：

```sh
uv run --locked --no-sync python -m vocoderbench.reference \
  --include-current-base --output runs/formal-hnm-v3-reference-120 \
  --threads 1 --seed 0 --timeout 10800 --stage mos --retry-failed
```

制御スクリプトは、合成側の `OMP_NUM_THREADS`、`OPENBLAS_NUM_THREADS`、`MKL_NUM_THREADS`、`NUMBA_NUM_THREADS` をすべて1にする。`HF_HUB_OFFLINE=1`、`TRANSFORMERS_OFFLINE=1` を使い、モデルを推論中に別途取得しない。uv・Hugging Face・Torch・Numba等のキャッシュ先も初回と同じ作業ツリー内の `.cache/` に固定する。実際の環境変数と完全な起動コマンドは保存された制御スクリプト全文を参照する。

`continue-formal-measurement.sh` は、回収の終了コードが非ゼロでも保存できた波形の評価は進め、最後に回収・評価それぞれのコードを `runs/formal-recovery-process.json` へ記録する。片方でも非ゼロなら全体は非ゼロとなる。評価が進んだことだけで、未完の方式まで完了扱いしない。

## 5. 保存先と再現可能性

制御スクリプトは測定packageや採用実装ではない。Git管理外でも処理内容を追跡できるよう、回収の開始時から `recovery/execution.json` に全文・SHA-256を記録した。今回は回収の最終保存まで達し、`preparation.json.recovery_execution` に全24起動を収め、`recovery_preserved_sha256` に初回成功ファイルの照合値も格納済み。初回最終状態の集計と終了記録も同じ公開対象JSONへ保存した。

本書作成時のSHA-256：

- `recover-formal-workers.py`：`7bf6a97d7553ed226853883b75709aa12cb464c60837b1c5c30e90a981651138`
- `continue-formal-measurement.sh`：`b39c706561adf7fb058160ad14130c13df34973ef844e1f6096be3f29ae30647`

回収本体の保存済み全文を使えば、実際の抽出・分割・起動・保存処理を復元できる。スクリプトは今回の出力先を指定しているため、別実験へ適用するときは出力先を新しくし、その制御スクリプトの変更とSHA-256も記録する。既存の回収フォルダを削除して同じ履歴を再利用しない。

| 記録 | 内容 |
|---|---|
| `contract.json` / `execution.json` | 凍結した測定条件・ソース・入力・開始情報 |
| `initial-stage-snapshot/snapshot.json` と同所の結果一式 | 初回終了時の件数・失敗状態・HTML/JSONの保全とSHA-256 |
| `recovery/initial-processes.json` / `initial-exit.json` | 初回3方式の失敗と初回段階の終了コード |
| `recovery/preserved-successful-sha256.json` | 回収前の成功JSON/npyの照合値 |
| `recovery/*-inputs.json` | 各まとまりの録音順序と入力仕様 |
| `recovery/*-implementation.json` | 初回・回収各起動の依存環境と初期化時間 |
| `recovery/execution.json` | 実行中の処理、全起動履歴、完全なコマンド、最終状態 |
| `logs/recovery-*.log` | 各ワーカーの標準出力・標準エラー |

公開物には原音全体・全長npy・学習済み重みを含めない。公開JSONだけから成功済み全長波形を復元して途中再開できるわけではない。途中再開には同じローカル実行の保存波形・入力・固定キャッシュが必要で、失われていれば新しい実行先で再測定し、別実験として記録する。

## 6. 解釈に残る限界

- 各まとまりの最初の録音には冷開始に伴う遅延が含まれ得る。モデル初期化そのものをRTFから除いていても、遅延初期化やキャッシュの影響まで除けたとは限らない。再起動を挟んだRTFを、全120録音を連続処理した同一条件の厳密速度比較と呼ばない。
- 回収に使う総所要時間には、繰り返すモデル読込、失敗した初回処理、評価、待機も含まれる。保存済みの解析・合成秒数やRTFとは別に記録する。
- プロセス分割で品質条件を意図的に変更しないが、内部状態に依存しないことを追加の一致測定で証明したわけではない。この未確認事項を隠さない。
- 未完を除いた744件だけで固定120録音×8方式の正式比較が完了したとは表示しない。回収後も未完・欠測があれば、方式別・指標別の予定分母を維持する。
- 回収処理の成功は品質優位、MOS校正、48 kHz原音への適用を示さない。元の研究計画の適用限界は変わらない。

## 7. 今後に活かす運用上の教訓

1. 長い比較では、音声ごとの保存と条件照合を最初から用意する。今回、成功済み744件を捨てずに続行できるのは逐次保存があるためである。
2. 1方式の停止を全方式の停止に広げない。成功済みの別方式と、実行可能な原音・合成音の評価を保持し、依存する未完分だけを回収する。
3. 観測した終了コードと原因の推定を分ける。メモリ増加とSIGKILLだけでOOMを断定しない。
4. 研究中に測定packageを修正して同じ結果フォルダへ継ぎ足さない。今回のように凍結ソースを維持した実行分割でも、変更した運用条件・初回の失敗・全起動履歴を保存する。
5. 今回は最大10件・24起動で全216件を回収できた。今後の長時間比較では、短いプロセスへ分割する設計を正式実行前に検討する。今回の成功だけで10件を無条件の恒久的な最適値にしない。恒久実装が必要なら測定終了後に別の変更として扱う。
6. 「継続中」は実プロセス・途中記録で、「完了」は予定数・個別状態・終了コード・保存物で判断する。回収スクリプトを用意しただけで測定完了と報告しない。

### 追加で観測した逐次保存のコスト

07:56 UTC台の `evaluation_partial.json` は28,197,442バイト（約26.9 MiB、約28.2 MB）だった。凍結済み `EvaluationCache.save` は1行を更新するたび、原音と全方式の途中結果全体を整形JSONへ直列化し、一時ファイルを書いて置換する。完了済み音響・MOSを再利用する録音でも、この全体保存が発生する。
