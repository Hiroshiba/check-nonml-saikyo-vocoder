# 開発ルール対応の往復レビュー

2026-10-11。方式の音質改善ではなく、既存の実行基盤にユーザーの開発ルールを適用した記録。

## 指摘・応答・再確認

1. 批評担当は、削除したテスト・requirements.txtをCIと文書がまだ参照すること、引数エラー本文がファイルログへ残らないこと、行数確認が直下ファイルしか拾わないことを指摘した。
2. 実装担当は、CI・文書をuv/Ruffと通常比較へ変更、共通の引数解析器でエラー本文と呼出しスタックを記録、Gitのファイル一覧から階層全体を列挙する修正を回答した。テストと合否監査は削除し、過去の測定記録は保持した。
3. 批評担当は追加確認で、Ruff出力をteeへ渡すと失敗を隠し得るため、CIのbashにpipefailが必要だと指摘した。ファイル一覧のNULをログでは改行へ変える案も出した。
4. 実装担当は `shell: bash` とログ用のNUL変換を適用した。批評担当は実ファイルを再確認し、重要指摘が解消したと回答した。実行・CI結果の確認を残す条件とした。

承認待ちを指示変更PRだけに限定し、許可済みの実装・調査まで停止しない運用も相互に確認した。#11の停止は、誤った自動承認判定を確認し直した後にも通常PRの処理を完了しなかった点が問題だった。今後は停止理由、実際の差分、継続可能な作業を分けて扱う。

## 実行で確認したこと

- キャッシュ付きRuffとソース行数確認が完了。
- WORLDの固定版ビルド確認とLLSMのビルドが完了。LLSM依存のCコードが出す警告もログへ保存された。
- 16 kHzの人工入力10種×4経路の40再合成、30操作、2手作り合成が処理失敗0で完了。これは既存の比較実行を用いた基盤確認であり、音質合格ではない。
- Pagesを生成し、2グループ・44件の内部リンクを確認した。保存済みの結果HTMLと測定JSONは変更していない。

次の研究実験からはユーザーの最新指定に従い、既存比較をWORLD（Harvest）だけにし、独自方式を初代ベースにする。この構成変更は別PRで扱う。

参考: [GitHub Actionsのシェル仕様](https://docs.github.com/ja/actions/reference/workflows-and-actions/workflow-syntax)。省略時と明示bashのpipefailの違いを批評担当が公式仕様で確認した。
