# 比較から改善へ進む手順

本書はAIによる運用文書。`USER_INSTRUCTIONS.md` が優先する。

## 現在の段階

まず既存の比較対象と比較方法を作る。公開方式を初めから勝者と決めず、同じ音声・前処理・測定器で再実行できるようにする。正式baseは `BASELINE.json` の一箇所で管理する。初代選定前は `method: null` と表示し、存在しないbase比較を作らない。初回レポートはこの状態と固定比較基準との差を明記する。

比較対象は複数維持できる。WORLDの解析器違い、LLSMの合成方式違い、測定器検査用のidentity・既知劣化は役割を区別する。identityは音声合成用のエンコードではなく、品質ランキングの候補にしない。

## 作業と記録

1. 調査担当は一次資料と公開議論を確認し、何が資料の主張で何が今回の推論かを分けて記録する。添付調査の件数を新たに再確認した件数として数えない。
2. 新手法・新構成は5人で議論する。批評家の反論、各担当の応答、未解決点、採否条件を残す。
3. 評価担当はコードとは独立に、変えたい性質、保持したい性質、適用範囲、欠測の扱いを決める。指標自体を既知の変換で検査する。
4. 実装担当は候補をリポジトリ外で実験する。依存関係はrevisionを固定し、データの出典・hash・前処理を記録する。
5. [日付・テーマ別の構成](../experiments/README.md) に従って記録する。比較実験はJSONとHTMLを出力する。失敗を含む全ケース、対象数、方式ごとの差、現在のbase、実行条件を保存する。
6. レビューで正常性・操作・再現・適用範囲を確認する。単一の音響指標や著者の品質主張で知覚品質の最良を決めない。
7. 良い新baseを採用するときは結果HTML、新実装、base情報更新、旧base削除を一つのPRにまとめる。不採用の場合は説明と結果だけを残す。

ユーザー指示変更はこの作業と別PRにする。ユーザー指示ファイルを変更するPRは、ユーザーレビュー後の明示的なマージ許可またはユーザー自身によるマージを待つ。それ以外のPRは対象ファイルとテスト結果を確認し、問題がなければAIがマージできる。

## 並行作業

音響調査、操作設計、独立評価、実装、批評を分担する。同じファイルを同時に編集せず、各担当の作業場所を分け、統合時にAPIと実測結果を確認する。並行する実験が古いbaseを使った場合は、採用前に最新baseで比較し直す。

## 停滞した場合

取得・ビルド・測定が失敗したら、実行条件とエラー、試した対応を `docs/STATUS.md` に残す。依存の切り分け、より小さい反例、他の比較対象の測定へ切り替える。失敗を隠してダミー結果を埋めない。

再開時は `USER_INSTRUCTIONS.md` → `docs/STATUS.md` → 最新結果HTMLの順に読む。次の作業と完了条件を具体的に残し、単なる「今後改善する」で終了しない。自動テストは後続の変更でも回せる形で維持する。

## 初代baseを選ぶ前の残課題

最初の少数発話と合成刺激は比較基盤の動作確認であり、広い音声分布に対する品質保証ではない。多話者・多言語・発声様式の追加、独立F0正解付きデータ、局所イベントや動的・複合操作、声質距離の根拠、既存人間評定と評価器の対応を順に確認する。未完了項目は結果に残し、ユーザー確認が必須という新しい承認ルールにはしない。
