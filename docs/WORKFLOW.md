# 比較から改善へ進む手順

本書はAIによる運用文書。`USER_INSTRUCTIONS.md` が優先する。

## 現在の段階

まず既存の比較対象と比較方法を作る。公開方式を初めから勝者と決めず、同じ音声・前処理・測定器で再実行できるようにする。開発baseは `BASELINE.json` の一箇所で管理する。その採用状態は既存方式に対する品質優位を意味しない。過去の初代選定前の記録は `method: null` のまま保持する。開発候補の採否比較では当時の開発ベースとの差を示す。既存方式だけの比較では自作ベースを測定・選定基準に含めない。

比較対象は複数維持できる。標準の既存比較対象はWORLD（Harvest）とFACodec、HiFi-Glot、GOLF-ff、SiFi-GAN、LLSM2 Layer 0、MagPhase。DACは明示指定時のみ。原音は測定と音声比較の参照として扱い、方式数に数えない。

## 作業と記録

HTMLと文書は日本語話者向けに説明する。専門語は初出で意味を補い、結果表には単位・値の読み方・欠測の意味を添える。機械処理用のIDやAPI名、出典の作品名、ライセンス原文は保持し、表示や周囲の文章で日本語の説明を加える。英語の識別子だけを読まないと結論が分からない構成にしない。

1. 調査担当は一次資料と公開議論を確認し、何が資料の主張で何が今回の推論かを分けて記録する。添付調査の件数を新たに再確認した件数として数えない。
2. 新手法・新構成は5人（1人は批評家）で議論する。提案→指摘→応答と修正→再確認を繰り返し、各論点を採用・棄却・未解決に分ける。一度の指摘で完了とせず、何が変わったかを相手が確認する。全員一致は要求せず、残った異論と採否条件を記録する。
3. 評価担当はコードとは独立に、変えたい性質、保持したい性質、適用範囲、欠測の扱いを決める。測定器の適用範囲や前処理の影響は、既知信号・変換に対する測定研究として記録する。
4. 実装担当は候補をリポジトリ外で実験する。依存関係はrevisionを固定し、データの出典・hash・前処理を記録する。候補ソース自体は採否までGit管理外に置き、実行前にソースのhashと変更点を測定記録へ保存する。
5. [グループの構成](../experiments/README.md) に従って記録する。比較実験はJSONとHTMLを出力する。失敗を含む全ケース、対象数、方式ごとの差、実行条件を保存する。開発候補の採否比較では当時のbaseも記録する。
6. レビューで正常性・操作・再現・適用範囲を確認する。単一の音響指標や著者の品質主張で知覚品質の最良を決めない。
7. 良い新baseを採用するときは結果HTML、新実装、base情報更新、旧base削除を一つのPRにまとめる。不採用の場合は説明と結果だけを残す。

ユーザー指示変更はこの作業と別PRにする。ユーザー指示ファイルを変更するPRは、ユーザーレビュー後の明示的なマージ許可またはユーザー自身によるマージを待つ。それ以外のPRは対象ファイルと静的解析・実行結果を確認し、問題がなければAIがマージできる。

今後のレポートは比較表と音声を冒頭に示し、一覧は保存済みの値・順位と短い音声を中心にし、用途別の折畳みで追加指標も辿れるようにする。一覧の比較差の列は省き、詳細の比較差・95%区間は保持する。過去の結果HTMLは表示変更のために再生成せず、当時の状態で保存する。

一覧では、予測音質・明瞭性・スペクトル・帯域の音量・音量変動・音量差など、異なる観点の結果を並べて改善と劣化を見比べられるようにする。検証条件や定型的な補足は詳細レポートで説明し、欠測がある値は一覧でも未測定・部分測定と分かる表示にする。タイトルは対象数や作業段階だけでなく、その実験で確かめたいテーマを伝える。複数候補を一つの実験で比べた場合、一覧の音声は代表候補・原音・当時のベース・WORLDに絞り、詳細で全候補を比較できるようにする。既存方式だけの比較では、その選択方式の音声を載せる。

## 並行作業

音響調査、操作設計、独立評価、実装、批評を分担する。同じファイルを同時に編集せず、各担当の作業場所を分け、統合時にAPIと実測結果を確認する。並行する開発候補の実験が古いbaseを使った場合は、採用前に最新baseで比較し直す。

## 承認待ちと継続作業を分ける

ユーザー指示ファイルを変更するPRだけがユーザーのレビュー・明示的なマージ許可待ちとなる。指示変更だけのPRを先に作ったら、すでに指示された実装や、そのPRに依存しない調査・測定は継続する。通常の実装PRはCIと差分を確認してAIがマージし、追加の承認待ちにしない。

承認チェックが拒否した場合は理由を確認する。実際の変更ファイルと指示ファイルの変更前後を調べ、拒否理由が事実と異なる新しい証拠を得た場合に限り、同じ操作を再試行する。別の経路で拒否を迂回しない。解消できなければ、その操作・拒否理由・ユーザーに必要な対応を具体的に伝え、他の許可済み作業を続ける。

進捗では「完了した作業」「承認待ちの対象」「続けている作業」を区別する。今回だけの作業指定は設定や作業記録へ反映し、ユーザー指示ファイルに恒久ルールとして追加しない。

## 停滞した場合

取得・ビルド・測定が失敗したら、実行条件とエラー、試した対応を `docs/STATUS.md` に残す。依存の切り分け、より小さい反例、他の比較対象の測定へ切り替える。失敗を隠してダミー結果を埋めない。

再開時は `USER_INSTRUCTIONS.md` → `docs/STATUS.md` → 最新結果HTMLの順に読む。次の作業と完了条件を具体的に残し、単なる「今後改善する」で終了しない。テストコード、スモーク・回帰・自己検査は実装しない。開発変更は静的解析と差分レビューで確認する。研究上必要な測定は目的・対象・条件を固定した実験として行い、コードの動作確認だけを目的に実行しない。

## 今後の品質評価の残課題

過去の少数発話による動作確認は当時の記録として保持する。新しい研究では多話者・多言語・発声様式の追加、独立F0正解付きデータ、局所イベントや動的・複合操作、声質距離の根拠、既存人間評定と評価器の対応を順に測る。未完了項目は結果に残し、ユーザー確認が必須という新しい承認ルールにはしない。


## 固定集合による比較

方式の採否に使う自然音声比較は [固定コーパス](CORPUS.md) の100録音以上で行う。小さな人工刺激は測定器の校正・音響特性の原因分析に使い、動作確認専用には使わない。現在の正式集合は英語40話者120録音。日本語12録音の補助集合は別の対象として表示する。入力を変える場合は別版として固定し、既存結果を書き換えない。

音響指標と [追加指標](EXTENDED_METRICS.md)、[自動MOS](MOS.md) を目的別に記録する。MOSは人の新しい評定ではなく予測値で、適用条件と未校正領域を併記する。指標を増やすこと自体を品質保証にせず、既知変換で測定器を校正する。原音のMOSも測り、低い点を理由に凍結後の入力を除外しない。

候補コード・指標・採否の考え方・モデル条件を全件測定の前に固定する。`python -m vocoderbench.benchmark --candidate-package /リポジトリ外の候補パッケージ --criteria /今回の判断条件.md --output runs/新しい比較` で、逐次保存しながら音響測定とMOSを実行する。科学条件が一致すれば同じ出力先で再開できる。`--retry-failed` は元の失敗を履歴へ残し、失敗だけ再実行する。未実行、処理失敗、個別指標の欠測を分けて表示する。

AIが設けた工学的な条件は、それ自体がユーザー要件や知覚劣化の境界とは限らない。条件の妥当性を結果後に見直した場合は、元の条件・測定・判定を保存し、新たな判断を事後の再検討として記録する。結果を見て条件を変えたのに、事前条件に合格したように書かない。振幅超過は頻度・対象録音・程度・局所変化を合わせて検討し、単一seedの新規超過だけを自動的な棄却条件にしない。これはAIの運用判断であり、ユーザーの新しい品質閾値ではない。

実行中は測定ソースを編集しない。文書のcommitが進んでも初回HEADは出典として維持し、科学条件はソースとデータのSHAで照合する。実装の不具合を修正した場合は新しい実行先で測り直し、旧実行の中断理由を残す。禁止された通信を別経路で迂回せず、取得済み資料でできる作業を続ける。

## 継続と完了の取り違えを防ぐ

個別PRのマージは工程の節目であり、研究全体の完成ではない。次の測定と判断根拠をSTATUSに書き、許可済みの次工程を実行する。停止や手戻りの原因と対策は [AIの作業メモ](AGENT_LESSONS.md) に残す。会話の終了後に実行される仕組みがない状態で、バックグラウンドでも続いているとは説明しない。

## 既存方式の比較入口

[REFERENCES.md](REFERENCES.md)の標準7方式を `python -m vocoderbench.reference --output ...` で比較する。既存方式への全置換も候補とし、現在の自作ベースを良いものと前提にしない。DACを加えるときだけ準備・実行の両方へ `--include-dac` を付ける。CIは静的解析だけを行い、正式比較の結果と自動MOSは研究実験で記録する。
