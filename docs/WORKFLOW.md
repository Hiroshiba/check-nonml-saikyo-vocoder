# 比較から改善へ進む手順

本書はAIによる運用文書。`USER_INSTRUCTIONS.md` が優先する。

## 現在の段階

まず既存の比較対象と比較方法を作る。公開方式を初めから勝者と決めず、同じ音声・前処理・測定器で再実行できるようにする。正式baseは `BASELINE.json` の一箇所で管理する。現在はユーザーの方針変更に従い、自作HNMを正式ベースとし、WORLD（Harvest）は既存比較対象にする。過去の初代選定前の記録は `method: null` のまま保持する。新しい比較では正式ベースとの差を示す。

比較対象は複数維持できる。現在選んでいる既存比較対象はWORLD（Harvest）のみ。原音は測定と音声比較の参照として扱い、方式数に数えない。

## 作業と記録

HTMLと文書は日本語話者向けに説明する。専門語は初出で意味を補い、結果表には単位・値の読み方・欠測の意味を添える。機械処理用のIDやAPI名、出典の作品名、ライセンス原文は保持し、表示や周囲の文章で日本語の説明を加える。英語の識別子だけを読まないと結論が分からない構成にしない。

1. 調査担当は一次資料と公開議論を確認し、何が資料の主張で何が今回の推論かを分けて記録する。添付調査の件数を新たに再確認した件数として数えない。
2. 新手法・新構成は5人（1人は批評家）で議論する。提案→指摘→応答と修正→再確認を繰り返し、各論点を採用・棄却・未解決に分ける。一度の指摘で完了とせず、何が変わったかを相手が確認する。全員一致は要求せず、残った異論と採否条件を記録する。
3. 評価担当はコードとは独立に、変えたい性質、保持したい性質、適用範囲、欠測の扱いを決める。指標自体を既知の変換で検査する。
4. 実装担当は候補をリポジトリ外で実験する。依存関係はrevisionを固定し、データの出典・hash・前処理を記録する。候補ソース自体は採否までGit管理外に置き、実行前にソースのhashと変更点を測定記録へ保存する。
5. [グループの構成](../experiments/README.md) に従って記録する。比較実験はJSONとHTMLを出力する。失敗を含む全ケース、対象数、方式ごとの差、現在のbase、実行条件を保存する。
6. レビューで正常性・操作・再現・適用範囲を確認する。単一の音響指標や著者の品質主張で知覚品質の最良を決めない。
7. 良い新baseを採用するときは結果HTML、新実装、base情報更新、旧base削除を一つのPRにまとめる。不採用の場合は説明と結果だけを残す。

ユーザー指示変更はこの作業と別PRにする。ユーザー指示ファイルを変更するPRは、ユーザーレビュー後の明示的なマージ許可またはユーザー自身によるマージを待つ。それ以外のPRは対象ファイルと静的解析・実行結果を確認し、問題がなければAIがマージできる。

今後のレポートは比較表と音声を冒頭に示し、一覧は主要指標・当時の比較差・短い音声に絞る。過去の結果HTMLは表示変更のために再生成せず、当時の状態で保存する。

## 並行作業

音響調査、操作設計、独立評価、実装、批評を分担する。同じファイルを同時に編集せず、各担当の作業場所を分け、統合時にAPIと実測結果を確認する。並行する実験が古いbaseを使った場合は、採用前に最新baseで比較し直す。

## 承認待ちと継続作業を分ける

ユーザー指示ファイルを変更するPRだけがユーザーのレビュー・明示的なマージ許可待ちとなる。指示変更だけのPRを先に作ったら、すでに指示された実装や、そのPRに依存しない調査・測定は継続する。通常の実装PRはCIと差分を確認してAIがマージし、追加の承認待ちにしない。

承認チェックが拒否した場合は理由を確認する。実際の変更ファイルと指示ファイルの変更前後を調べ、拒否理由が事実と異なる新しい証拠を得た場合に限り、同じ操作を再試行する。別の経路で拒否を迂回しない。解消できなければ、その操作・拒否理由・ユーザーに必要な対応を具体的に伝え、他の許可済み作業を続ける。

進捗では「完了した作業」「承認待ちの対象」「続けている作業」を区別する。今回だけの作業指定は設定や作業記録へ反映し、ユーザー指示ファイルに恒久ルールとして追加しない。

## 停滞した場合

取得・ビルド・測定が失敗したら、実行条件とエラー、試した対応を `docs/STATUS.md` に残す。依存の切り分け、より小さい反例、他の比較対象の測定へ切り替える。失敗を隠してダミー結果を埋めない。

再開時は `USER_INSTRUCTIONS.md` → `docs/STATUS.md` → 最新結果HTMLの順に読む。次の作業と完了条件を具体的に残し、単なる「今後改善する」で終了しない。テストコードは実装しない。静的解析と通常の実験実行で変更の影響を確認し、音響測定の正常終了を品質合格とは扱わない。

## 今後の品質評価の残課題

最初の少数発話と合成刺激は比較基盤の動作確認であり、広い音声分布に対する品質保証ではない。多話者・多言語・発声様式の追加、独立F0正解付きデータ、局所イベントや動的・複合操作、声質距離の根拠、既存人間評定と評価器の対応を順に確認する。未完了項目は結果に残し、ユーザー確認が必須という新しい承認ルールにはしない。
